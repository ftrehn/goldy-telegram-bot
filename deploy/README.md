# Выкладка

Бот, воркер, планировщик, приёмник каталога и сидер каталога — один образ и пять
команд. Собирается он из корня репозитория, версию берёт из git, работает не от
root. Всё, что отличает боевой запуск от локального, живёт в `.env`; в самих файлах
нет ни одного пароля по умолчанию, и это намеренно: compose, поднимающийся с
`guest/guest`, превращает RabbitMQ на публичном адресе в чужую майнинг-ферму за
сутки.

## Что нужно на сервере

Docker с плагином compose и больше ничего. Python, uv и just на сервере не нужны —
всё это остаётся в сборочной стадии образа.

## Первая установка

```sh
git clone <репозиторий> goldy && cd goldy
cp .env.example .env
# заполнить: TELEGRAM_BOT_TOKEN, POSTGRES_PASSWORD, RABBITMQ_USER, RABBITMQ_PASSWORD,
# GOLDY_DEFAULT_PRICE_TYPE_ID, GOLDY_ADMIN_PHONE_NUMBERS, GOLDY_CATALOG_RECEIVER_TOKEN
docker compose up -d --build
```

Миграции накатываются отдельным одноразовым сервисом `migrate`, и четыре постоянных
процесса ждут его завершения. Запускать `alembic upgrade head` из точки входа бота
нельзя: четыре процесса на каждом рестарте гонялись бы за одним замком.

Каталог наполняет сама 1С: регламентное задание расширения `ГолдиБот` шлёт пачки
по HTTP в сервис `catalog-receiver`. Со стороны сервера бота для этого нужны две
вещи: токен в `GOLDY_CATALOG_RECEIVER_TOKEN`, тот же, что записан в константу
`гб_ТокенБота` расширения, и адрес приёмника, достижимый с сервера 1С (раздел
«Приёмник каталога снаружи» ниже). Как загрузить расширение в базу и заполнить
его константы — [integrations/1c/README.md](../integrations/1c/README.md).

Пока 1С не подключена или для проверки на снимке, проекцию можно наполнить и
руками, тем же контрактом:

```sh
docker compose run --rm bot python -m goldy.catalog_seed_app --file snapshot.json
```

## Приёмник каталога снаружи

Приёмник — единственный сервис, у которого есть входящие соединения, и
единственный, который публикует порт: `${GOLDY_CATALOG_RECEIVER_PORT:-8090}` на
хосте ведёт на `8090` в контейнере. Сам он говорит по HTTP без TLS, и наружу его в
таком виде выставлять нельзя: токен в заголовке `Authorization` уходил бы открытым
текстом, а это единственная защита каталога от переписывания кем угодно. Перед
ним ставится обратный прокси с TLS — nginx, Caddy, что угодно, что умеет
проксировать один путь, — и на сервере 1С в константу `гб_АдресБота` записывается
адрес прокси вида `https://bot.example.ru`. Если сервер 1С и сервер бота в одной
частной сети, достаточно закрыть порт снаружи файрволом и дать 1С внутренний адрес
по HTTP.

Что должен пропускать прокси: `GET /catalog/ping` и `POST /catalog/batches` с
любым хвостом пути, с телом до `GOLDY_CATALOG_RECEIVER_MAX_BODY_MIB` мебибайт (по
умолчанию 64) — у nginx это `client_max_body_size`, иначе прокси ответит 413
раньше приёмника. Таймаут ответа ставьте с запасом, минуты две: пачка в две тысячи
цен пишется одной транзакцией, и ответ уходит только после коммита — 1С ждёт
именно его, чтобы решить, слать ли следующую.

## Обновление

```sh
git pull
docker compose up -d --build
```

Сервис `migrate` отработает заново и применит новые ревизии до того, как поднимутся
бот, воркер, планировщик и приёмник. Простой равен времени пересоздания
контейнеров; прогон 1С, попавший на это окно, оборвётся с ошибкой соединения и
повторится по расписанию задания.

## Что проверить после первого запуска

Логи `migrate` обязаны закончиться применённой ревизией, а не исключением. `docker
compose ps` показывает `bot`, `worker`, `scheduler` и `catalog-receiver` в
состоянии `running`, а `postgres`, `redis` и `rabbitmq` — `healthy`. В Telegram
`/start` с телефона администратора обязан выдать роль администратора: номера из
`GOLDY_ADMIN_PHONE_NUMBERS` применяются и при старте процесса, и при регистрации.

Приёмник проверяется двумя запросами с сервера 1С или с любой машины, откуда 1С
будет ходить: `curl -i https://<адрес>/catalog/ping` без заголовка обязан вернуть
`401`, с `-H "Authorization: Bearer <токен>"` — `200` и `{"status": "ok"}`. Полный
чек-лист с пачкой и финализацией — раздел «Проверка приёмника каталога руками» в
[docs/manual-check.md](../docs/manual-check.md). После этого в 1С достаточно
выполнить регламентное задание «Выгрузка каталога в Голди-бот» один раз руками и
прочитать его отчёт в журнале регистрации.

## Чего здесь сознательно нет

Обратного прокси в самом compose: какой именно и с каким сертификатом — решение
конкретного сервера, а не репозитория. Нужен он одному сервису, приёмнику
каталога; бот работает на long polling и сам ходит к Telegram, воркер и
планировщик наружу не смотрят вовсе.

Секретов в git: `.env` исключён и из репозитория, и из контекста сборки. На сервере
он создаётся руками один раз.

## Технические детали

- Образ: `python:3.14-slim`, две стадии, зависимости ставятся из `uv.lock` отдельным
  слоем и переживают правки кода.
- В сборочной стадии стоит `git` — `hatch-vcs` вызывает его, чтобы получить версию;
  в рантайм-образ он не попадает.
- Пользователь `goldy`, uid и gid 1000 — числовой, чтобы права на смонтированный том
  можно было сопоставить с хостом.
- Размер образа около 380 МБ.
- Тома: `postgres_data`, `redis_data`, `rabbitmq_data`.
- Порты наружу публикует один сервис — `catalog-receiver`,
  `${GOLDY_CATALOG_RECEIVER_PORT:-8090}:8090`; остальные не публикуют ничего.
