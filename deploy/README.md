# Выкладка

Бот, воркер, планировщик, приёмник каталога и сидер каталога — один образ и пять
команд. Собирается он из корня репозитория, версию берёт из git, работает не от
root. Всё, что отличает боевой запуск от локального, живёт в `.env`; в самих файлах
нет ни одного пароля по умолчанию, и это намеренно: compose, поднимающийся с
`guest/guest`, превращает RabbitMQ на публичном адресе в чужую майнинг-ферму за
сутки.

## Что нужно на сервере

Docker с плагином compose и больше ничего. Python, uv и just на сервере не нужны —
всё это остаётся в сборочной стадии образа.

## Первая установка

```sh
git clone <репозиторий> goldy && cd goldy
cp .env.example .env
# заполнить: TELEGRAM_BOT_TOKEN, POSTGRES_PASSWORD, RABBITMQ_USER, RABBITMQ_PASSWORD,
# GOLDY_DEFAULT_PRICE_TYPE_ID, GOLDY_ADMIN_PHONE_NUMBERS, GOLDY_CATALOG_RECEIVER_TOKEN
docker compose up -d --build
```

Миграции накатываются отдельным одноразовым сервисом `migrate`, и четыре постоянных
процесса ждут его завершения. Запускать `alembic upgrade head` из точки входа бота
нельзя: четыре процесса на каждом рестарте гонялись бы за одним замком.

Каталог наполняет сама 1С: регламентное задание расширения `ГолдиБот` шлёт пачки
по HTTP в сервис `catalog-receiver`. Со стороны сервера бота для этого нужны две
вещи: токен в `GOLDY_CATALOG_RECEIVER_TOKEN`, тот же, что записан в константу
`гб_ТокенБота` расширения, и адрес приёмника, достижимый с сервера 1С (раздел
«Приёмник каталога снаружи» ниже). Как загрузить расширение в базу и заполнить
его константы — [integrations/1c/README.md](../integrations/1c/README.md).

Пока 1С не подключена или для проверки на снимке, проекцию можно наполнить и
руками, тем же контрактом:

```sh
docker compose run --rm bot python -m goldy.catalog_seed_app --file snapshot.json
```

## Приёмник каталога снаружи

Приёмник — единственный сервис, у которого есть входящие соединения, и
единственный, который публикует порт: `${GOLDY_CATALOG_RECEIVER_PORT:-8090}` на
хосте ведёт на `8090` в контейнере. Сам он говорит по HTTP без TLS, и наружу его в
таком виде выставлять нельзя: токен в заголовке `Authorization` уходил бы открытым
текстом, а это единственная защита каталога от переписывания кем угодно. Перед
ним ставится обратный прокси с TLS — nginx, Caddy, что угодно, что умеет
проксировать один путь, — и на сервере 1С в константу `гб_АдресБота` записывается
адрес прокси вида `https://bot.example.ru`. Если сервер 1С и сервер бота в одной
частной сети, достаточно закрыть порт снаружи файрволом и дать 1С внутренний адрес
по HTTP.

Что должен пропускать прокси: `GET /catalog/ping` и `POST /catalog/batches` с
любым хвостом пути, с телом до `GOLDY_CATALOG_RECEIVER_MAX_BODY_MIB` мебибайт (по
умолчанию 64) — у nginx это `client_max_body_size`, иначе прокси ответит 413
раньше приёмника. Таймаут ответа ставьте с запасом, минуты две: пачка в две тысячи
цен пишется одной транзакцией, и ответ уходит только после коммита — 1С ждёт
именно его, чтобы решить, слать ли следующую.

## Обновление

```sh
git pull
docker compose up -d --build
```

Сервис `migrate` отработает заново и применит новые ревизии до того, как поднимутся
бот, воркер, планировщик и приёмник. Простой равен времени пересоздания
контейнеров; прогон 1С, попавший на это окно, оборвётся с ошибкой соединения и
повторится по расписанию задания.

## Beget

Боевой сервер — VPS на Beget, и бот на нём не один: рядом работают ещё два
проекта, чат-агент и аналитика Ozon, и общего у них ровно одно — обратный прокси.
Один Caddy на весь сервер держит порты 80 и 443, выпускает сертификаты Let's
Encrypt и терминирует TLS для всех доменов сразу. Живёт он в `/opt/edge`: главный
Caddyfile там состоит из одной строки `import sites/*.caddy`, а каждый проект
кладёт в `/opt/edge/sites` свой файл с описанием своего домена. Переменные для
этих файлов — домены, хэши паролей — собраны в `/opt/edge/.env`. С контейнерами
проектов Caddy встречается во внешней docker-сети `edge`. Она создана на сервере
один раз и не принадлежит ни одному compose-проекту, поэтому переживает
пересоздание любого из них. Этот репозиторий лежит в `/opt/goldy-bot`.

Поверх `docker-compose.yaml` на сервере накладывается второй файл,
`docker-compose.prod.yml`, и запуск выглядит так:

```sh
cd /opt/goldy-bot
docker compose -f docker-compose.yaml -f docker-compose.prod.yml up -d --build
```

Второй файл — overlay: compose сливает его с первым ключ за ключом, и в нём
записано только то, что меняет общий сервер. Меняет он три вещи. Публикация порта
приёмника снимается: файрвола на сервере нет, а Docker пишет свои DNAT-правила
мимо ufw, так что опубликованный порт — это открытый порт, и закрывать его
снаружи бесполезно. Вместо этого приёмник подключается к сети `edge` под именем
`goldy-receiver`, и только по этому имени его видит Caddy; своё compose-имя
`catalog-receiver` он в общей сети не объявляет, чтобы не пересечься с чужим
сервисом. Логи каждого контейнера ограничиваются по размеру и числу файлов:
драйвер json-file по умолчанию хранит всё, и бот, который пишет каждое
обновление, за несколько месяцев заполняет диск. На каждый сервис ставится
потолок по памяти. Процесс, который до него дорос, будет убит и перезапущен
своей же политикой рестарта, а не ядром, выбирающим жертву среди трёх проектов
сразу.

Сниппет Caddy для приёмника хранится в репозитории, `deploy/caddy/goldy-bot.caddy`,
и копируется в `/opt/edge/sites/`. Он пропускает к приёмнику только пути
`/catalog/*` и на всё остальное отвечает 404, не тревожа приёмник. Лимит тела
запроса в нём выставлен чуть выше лимита самого приёмника, чтобы 413 отдавал
тот, кто его и объяснит. Таймаут ожидания ответа — три минуты, под транзакцию
пачки из раздела «Приёмник каталога снаружи». Домен сниппет берёт из переменной
`GOLDY_RECEIVER_DOMAIN`, которую надо добавить в `/opt/edge/.env`. Новую
переменную Caddy увидит только после пересоздания контейнера — `docker compose
up -d` в `/opt/edge`, это секунды простоя для всех доменов сразу; правку самого
сниппета он перечитывает без остановки командой `caddy reload`. Этот же домен
записывается в 1С в константу `гб_АдресБота`.

К Telegram бот ходит не напрямую, а через туннель до второго, маленького
сервера в Нидерландах. Это страховка на случай, если `api.telegram.org` перестанет
отвечать с российского адреса: к Telegram ходят бот, за обновлениями, и воркер, с
уведомлениями, и оба уходят в туннель. Планировщик читает ту же переменную только
потому, что собирает контейнер воркера; сам он в Telegram не пишет.

Открытый SOCKS5 между серверами не годится: на этом пути стоит DPI, и он рвёт
поток, если в команде CONNECT встречается адрес Telegram — проверено, проходило
две попытки из шести. Поэтому на Beget в `/opt/tunnel` работает Xray-клиент,
контейнер `tg-proxy`: боту он отдаёт обычный SOCKS5 внутри docker-сети `tgproxy`,
а наружу заворачивает всё в VLESS + Reality до нидерландского сервера. Для DPI
это TLS-соединение к `github.com` с настоящим сертификатом GitHub, отличить его
от настоящего без ключа нельзя. Клиент раз в полминуты проверяет туннель и,
если тот недоступен, переключает выход на прямой; когда туннель возвращается —
обратно. Бот об этом не знает: у него один адрес прокси. Адрес задаётся
переменной `TELEGRAM_PROXY_URL` в `.env` бота, значение вида
`socks5://goldy-bot:pass@tg-proxy:1080`; пароль лежит только в `.env` и в
`/opt/tunnel/config.json`, в репозитории его нет.

Обновление — то же, что в разделе «Обновление», только с двумя файлами.
Репозиторий на сервере клонирован через deploy-ключ: это отдельная пара
SSH-ключей, которой на GitHub дано право только читать один этот репозиторий,
чтобы сервер не хранил ключ от всего аккаунта. Ключ подключён алиасом
`github-goldy` в `/root/.ssh/config`, и в адресе `origin` вместо `github.com`
стоит этот алиас.

```sh
cd /opt/goldy-bot
git pull
docker compose -f docker-compose.yaml -f docker-compose.prod.yml up -d --build
```

Технические детали:

- Сервер: Beget, Ubuntu 24.04, 6 vCPU, 12 ГБ, Docker 29, compose v5.5; ufw
  неактивен.
- Общий Caddy: `/opt/edge`, Caddyfile — `import sites/*.caddy`, переменные в
  `/opt/edge/.env`; сеть `edge` создаётся один раз: `docker network create edge`.
- Сниппет: `deploy/caddy/goldy-bot.caddy` → `/opt/edge/sites/goldy-bot.caddy`;
  переменная `GOLDY_RECEIVER_DOMAIN`; правку сниппета перечитать без остановки:
  `docker exec edge_caddy caddy reload --config /etc/caddy/Caddyfile`; новую
  переменную в `.env` — `cd /opt/edge && docker compose up -d`.
- Имя приёмника в сети `edge`: `goldy-receiver`, порт `8090` в контейнере;
  на хост не публикуется (`ports: !override []`).
- Лимиты памяти: bot 512m, worker 512m, scheduler 256m, catalog-receiver 512m,
  postgres 1g, redis 256m, rabbitmq 768m; migrate без лимита. В сумме 3,75 ГБ.
- Логи, json-file: 10m × 2 — migrate, scheduler, redis; 20m × 3 — bot,
  catalog-receiver, postgres, rabbitmq; 50m × 5 — worker.
- Caddy: `/catalog/*` → `goldy-receiver:8090`, остальное — 404;
  `request_body max_size 70MB`; `response_header_timeout 180s`;
  `Strict-Transport-Security "max-age=31536000"`.
- Туннель к Telegram: `/opt/tunnel/docker-compose.yml`, контейнер `tg-proxy`
  (Xray, SOCKS5 на `tg-proxy:1080` в сети `tgproxy`, наружу VLESS + Reality до
  нидерландского сервера, порт 443, SNI `github.com`); адрес сервера и ключи —
  в `/opt/tunnel/config.json`, парные — в `/usr/local/etc/xray/config.json`
  на нидерландском сервере; в репозитории ни того, ни другого нет.
  `TELEGRAM_PROXY_URL=socks5://goldy-bot:pass@tg-proxy:1080` в `.env` бота.
- Сеть `tgproxy` создаётся один раз: `docker network create tgproxy`; в неё
  overlay подключает bot, worker и scheduler.
- Deploy-ключ: в `/root/.ssh/config` блок `Host github-goldy` с
  `HostName github.com` и `IdentityFile` на приватный ключ; `origin` —
  `git@github-goldy:ftrehn/goldy-telegram-bot.git`.

## Что проверить после первого запуска

Логи `migrate` обязаны закончиться применённой ревизией, а не исключением. `docker
compose ps` показывает `bot`, `worker`, `scheduler` и `catalog-receiver` в
состоянии `running`, а `postgres`, `redis` и `rabbitmq` — `healthy`. В Telegram
`/start` с телефона администратора обязан выдать роль администратора: номера из
`GOLDY_ADMIN_PHONE_NUMBERS` применяются и при старте процесса, и при регистрации.

Приёмник проверяется двумя запросами с сервера 1С или с любой машины, откуда 1С
будет ходить: `curl -i https://<адрес>/catalog/ping` без заголовка обязан вернуть
`401`, с `-H "Authorization: Bearer <токен>"` — `200` и `{"status": "ok"}`. Полный
чек-лист с пачкой и финализацией — раздел «Проверка приёмника каталога руками» в
[docs/manual-check.md](../docs/manual-check.md). После этого в 1С достаточно
выполнить регламентное задание «Выгрузка каталога в Голди-бот» один раз руками и
прочитать его отчёт в журнале регистрации.

## Чего здесь сознательно нет

Обратного прокси в самом compose: какой именно и с каким сертификатом — решение
конкретного сервера, а не репозитория. Нужен он одному сервису, приёмнику
каталога; бот работает на long polling и сам ходит к Telegram, воркер и
планировщик наружу не смотрят вовсе. На Beget это остаётся верным: Caddy там
живёт в `/opt/edge` как общий для всех проектов сервера, а в репозитории
хранится только сниппет его конфигурации для приёмника.

Секретов в git: `.env` исключён и из репозитория, и из контекста сборки. На сервере
он создаётся руками один раз.

## Технические детали

- Образ: `python:3.14-slim`, две стадии, зависимости ставятся из `uv.lock` отдельным
  слоем и переживают правки кода.
- В сборочной стадии стоит `git` — `hatch-vcs` вызывает его, чтобы получить версию;
  в рантайм-образ он не попадает.
- Пользователь `goldy`, uid и gid 1000 — числовой, чтобы права на смонтированный том
  можно было сопоставить с хостом.
- Размер образа около 380 МБ.
- Тома: `postgres_data`, `redis_data`, `rabbitmq_data`.
- Порты наружу публикует один сервис — `catalog-receiver`,
  `${GOLDY_CATALOG_RECEIVER_PORT:-8090}:8090`; остальные не публикуют ничего.
  Боевой overlay `docker-compose.prod.yml` снимает и эту публикацию — на Beget
  к приёмнику ходит только Caddy по сети `edge`.
